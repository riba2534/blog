> 换掉一块木板容易。难的是船还在海上，动手的还是船上的水手。

普鲁塔克在《忒修斯传》里记下过那条船：雅典人为了纪念忒修斯，把他的船一直保存着，朽坏一块木板就换一块新的，年复一年，直到有人发问，所有木板都换过一遍之后，这还是忒修斯的船吗？

2026 年 8 月 13 日，DeepSeek 开源了自家的 agent harness，命令行名字叫 `dsh`，随它一起发布的还有一篇学术论文。把代码和论文放在一起读完会发现，这个团队认真回答的正是忒修斯之船的工程版本：**一个正在运行的系统，能不能在不靠岸的前提下，安全地换掉自己的任何一块木板？** 主循环算一块，模型自己写出来的插件也算一块。

![航行中换板的船](https://img.riba2534.cn/images/2026/08/dsh-theseus-01-ship.png)

*船在动，港口不在画面里。*

这个项目从第一次提交到对外发布只隔了两个月。论文标题是《A Programming Paradigm for Spatiotemporal Composability》，时空可组合性的编程范式，署名来自北京大学与 DeepSeek-AI。论文形式化的对象叫 Cordis，一个插件框架，随 dsh 一同分发，dsh 的全部能力都搭在它上面。船板可以边航行边换，Cordis 是那套换板工艺，dsh 是用这套工艺造出来的船。

## 换零件为什么这么难

从一个所有人都体验过的现象说起：VSCode 装插件不用重启，卸载插件却经常弹出"请重新加载窗口"。

看一组数据（2026 年 6 月的 VS Code 插件市场）：安装量前 100 的扩展里，87 个包含可执行代码。VS Code 的所有扩展共享同一个宿主进程，装上去容易，请下去难。宿主没有任何机制在运行时卸载单个扩展的代码，禁用或卸载都要重启整个扩展宿主，殃及所有已加载的扩展。

问题出在哪？扩展启动时干了一堆事：注册命令、挂监听器、开连接、改共享状态。系统只看到这些动作发生了，看不到怎么撤销它们。VS Code 给了一个 `deactivate` 钩子让扩展自己收拾，但这个钩子只在宿主进程退出时作为善后回调运行，压根不用于活体卸载；而且它把"效果的销毁"和"效果的创建"拆在两个函数里，创建时干了十件事，销毁时记得撤八件，剩下两件就成了幽灵，没有任何机制能验证清理是否完整。

依赖那一侧的情况也好不到哪去。VS Code 提供了 `extensionDependencies` 字段，前 100 的扩展里只有 7 个用它声明过对非内置扩展的依赖。扩展之间想互相调用，要走 `getExtension(...).exports`，拿到手的类型是 `any`，契约无从谈起。

对传统软件，这只是体验问题，重启一下扩展宿主，几秒钟的事。放到 AI agent 身上，同样的问题就换了量级。

先解释一下 agent harness 这个词。模型本身只会输出文字，要让它真正干活，需要一层运行时替它跑腿：组装提示词、执行工具调用、管理会话与权限、编排子任务、对接用户界面。这层运行时就是 harness，模型的马具。市面上每个 agent 产品底下都有这么一层，只是大多没有名字。

agent 的下一步演化方向已经清楚：模型在运行中给自己写工具、改自己的插件、调整自己的组合。每一次这样的自我修改都是一次运行时换零件。如果每次都要重启，会话状态、正在执行的任务、积累的缓存全部清零，而自我修改的频率是连续的，系统会在无穷无尽的重启里失去可用性。

还有一种更要命的情况：一次写错的自我修改，可能把负责恢复的那个进程本身搞挂。

## 重启这笔账

运行时换零件的需求存在了几十年，一直没有像样的理论，原因是凑合的办法够用。操作系统在进程粒度上提供了"时间"这一侧的能力，进程行为不对就杀掉重启，它的所有资源由内核统一回收；容器编排在服务粒度上提供了"空间"这一侧的能力，服务之间的依赖交给编排器，谁挂了拉起谁。绝大多数软件靠这两样活得不错。

代价被摊平在日常里，很少有人专门算。每次重启丢掉全部进程内状态，缓存、连接、算了一半的结果，重建要几秒到几分钟；重启期间要维持可用性，就得多养冗余副本。容器级的编排表达不了同一个进程地址空间里组件之间的依赖，还把本来一次函数调用能解决的交互压上了网络。

粒度错配是关键。进程和容器的边界太粗，而现代系统想要的组合粒度越来越细。agent 自我修改把错配推到了极端：修改的单元是一个工具、一个插件，代价却是整个进程陪葬，重启完还得指望一切自己长回原样。

细粒度的运行时组合一直缺一块理论地基。

## 时间与空间：两个正交的问题

"运行时增删组件"这个大问题，可以拆成两问。第一问：组件拆走时，它干过的事能不能撤干净？第二问：组件依赖别人，别人来了、走了、换了怎么办？

第一问，从租房说起。租客入住时搬家具、钉钉子、换门锁，退租时房东希望房子恢复原样。靠谱的做法是每做一件事，当场留一张"后悔药"：搬进沙发的同时写下"届时把沙发搬走"，钉钉子的同时写下"届时拔钉子补墙"。退租时把这沓后悔药倒着执行一遍，后干的先撤，房子就还原了。

![每个改动带着撤销方法进场](https://img.riba2534.cn/images/2026/08/dsh-theseus-03-reverse.png)

*进场时写下的那张纸，退场时才第一次被读到。*

形式上，一个可逆效应的类型是"当前状态 → 新状态 × 撤销函数"。撤销函数由调用者在动手的那一刻提供，运行时负责把它们攒起来，按后进先出的顺序复合。这个设计带来一个结构性的收益：**组件的清理逻辑从它的启动逻辑里自动推导出来，无需单独编写**。启动干了十件事，后悔药就有十张。VS Code 那种创建与销毁分离的裂缝，从根上就不存在了。

第二问像电网。电器出厂时不关心哪座电站供电，它声明"需要电"；插上标准插座，供电到位就工作，停电就待机，换了电站就重新上电。组件也一样：声明自己依赖哪些服务，运行时盯着环境变化，把每次变化对着声明分类，满足了就激活你，失去了就先停你，无关就不理你。

![依赖声明与反应式激活](https://img.riba2534.cn/images/2026/08/dsh-theseus-04-inject.png)

*依赖是声明出来的，激活由满足关系驱动，组件自己不用盯着电闸。*

拆除一个提供方时，直觉的做法是立刻撤掉它的服务，这里却拆成了两步：第一步只宣布"要走了"，停止对外提供，让依赖它的组件先开始各自的收尾；第二步等所有依赖者都撤完，提供方才真正执行自己的撤销。为什么？拿连接池想一想就明白：关闭连接池的时候，手里的连接要还给池子。池子先没了，还给谁？

两问在论文里各有名字：

| 维度 | 问的问题 | 机制 |
|---|---|---|
| 时间（Temporal） | 组件拆走时，它干过的事能不能撤干净？ | Revertible effects，可逆效应 |
| 空间（Spatial） | 组件依赖别人，别人来了、走了、换了怎么办？ | Reactive coeffects，反应式协效应 |

effect 和 coeffect 是编程语言理论里的一对老概念：effect 描述计算如何修改环境，coeffect 描述计算如何依赖环境，经典做法把它们放进类型系统做编译期分析。这里换了个思路：把这两个概念物化成运行时可以直接操作的实体，让静态系统提供的保证在动态场景里成立。

> we reify the conceptual structures of effects and coeffects so that a runtime can operate on them directly, establishing dynamically the guarantees these systems provide statically.

两把机制之外还有一对配件。同一个依赖名，能不能在不同作用域里解析到不同的实例？解法叫隔离域（realm）：多租户系统里两个租户各用各的数据库连接，测试环境把真实服务换成假实现，互不干扰，且这种多态可以在运行时动态调整。

另一件配件叫拦截（interception）：在不改双方代码的前提下，给依赖的每次调用附加元数据。典型的用法是访问控制，文件系统依赖可以携带一份"这个组件只许读写哪些路径"的说明，提供方逐次调用时核对。约束住在组合配置上，随时装卸，既不触碰任何一方的源码，也不触发任何重载。

## 后悔药的细节

撤销真能恢复"原状"吗？`free` 把内存块还给分配器，但堆的布局回不到 `malloc` 之前；生成过的唯一 ID 也不会因为撤销而被收回。物理上的原状恢复不了。出路是把所有"状态相等"放宽为观察等价：只要没有任何观察者能分辨出区别，就算恢复了。而观察者能看到什么，恰好由声明出来的依赖决定，堆布局没有被任何依赖暴露，所以它压根不在"原状"的定义里。这个定义把还原的标准从物理状态挪到了系统实际承诺的观察面上。

多个组件的效果交错堆叠，还能单独撤掉其中一个吗？倒序撤销只在"最后进来的最先走"时天然成立，可现实是组件 A 和 B 的效果穿插在一起，偏偏想先拆 A。这在数学上是个交换性问题：A 的撤销函数会碰到被 B 改过的状态。好在有一个经过严格证明的实用判据：只要两个组件触碰的每个共享位置都满足"操作可交换"，按任意顺序撤销就都能回到起点。

哪些位置可交换？判据落到工程上非常好认。值是"一张可独立增删条目的表"的位置，天然可交换：路由表、事件监听器列表，两个组件各注册一条，谁先谁后无所谓，谁先撤谁后撤也无所谓。值是"一条有序链"的位置，天然不可交换：middleware 链里插在前面的那个会看到不同的请求，怎么撤都会扰动别人。

agent 运行时的核心结构恰好就是一堆注册表：工具注册表、模型适配器注册表、提示词片段注册表，全是可独立增删的表。也就是说，agent harness 的主体天然落在理论的安全区里；剩下那些顺序敏感的部分，交给显式的依赖声明去约束。

拆到一半，目标变了怎么办？组件正在加载，它依赖的服务突然没了；或者正在卸载，依赖又回来了。组件的生命周期因此被建成带"惯性"的状态机：一次开始的转移必须跑到确定点，中途目标变了，先落地，再掉头。失败的处理原则叫"先恢复、再记录"：加载失败的组件把已经做过的部分撤干净，错误记在自己身上，兄弟组件照常运行。

## 折腾不留痕

上面的机制拼起来，指向整套理论的皇冠定理：Confluence。

> whatever sequence of activations and deactivations a running system has been through, the state it quiesces at is the one the same insertions and retirements would have produced had each component that ends up active been loaded once, in dependency order, and none ever unloaded.

翻译成人话：不管系统运行中装了拆、拆了装、换了多少轮，只要它最终静止下来，状态就等于按最终清单一次性装好的状态。**不管中途折腾过什么，最终状态只看当前这份清单。**

![两条路径，同一终点](https://img.riba2534.cn/images/2026/08/dsh-theseus-05-confluence.png)

*绕多远的路，终点是同一座城堡。*

定理买断的是"理解历史"的成本。运维一个长期运行的系统，最怕听到的一句话是"这台机器的状态说不清，是这些年折腾出来的"。Confluence 从数学上取缔了这句话：想知道系统现在什么样，看当前配置清单就够了，折腾史无关紧要。

对一个会自我修改的 agent，这层保证还有更实际的含义：模型试错时装上又拆掉的工具、失败后回滚的插件，都不会在系统里留下暗伤，最终起作用的只有活下来的那个组合。

支撑定理的演算里，外部输入只有插入和退休两种，其余全是系统的自发转移。定理有前提：依赖图无环、效应满足交换性判据、组件如实声明和提供。定理不覆盖失败的组件，因为失败与调度时序有关；好在失败组件对状态的贡献已被恢复机制清零，除了"它失败了"这个标记，什么也不留。

理论的证据在哪？Cordis 早已在生产环境泡了多年，它支撑着一个叫 Koishi 的开源聊天机器人框架，四年时间、4000 多个社区插件，插件在运行的进程里启停、热重载、换实现（严格说，Koishi 验证的是上一代 Cordis，论文形式化的是重新设计后的这一代，核心组合模型两代共享）。作者们自己承认这只是"存在性与被采纳"层面的证据，缺少定量对照实验，而自演化 agent harness 场景的验证被列为未来工作。论文与 dsh 同日发布。许愿与还愿之间，隔了零天。

## 把定理装进运行时

理论看完，往上一层：Cordis 把这些机制做成了什么样的 API？一个插件长这样：

```typescript
export const name = 'my-plugin'
export const inject = ['tools', 'llm']     // 空间维度：声明依赖

export function apply(ctx) {               // ctx 是插件看世界的唯一窗口
  ctx.effect(() => {                       // 时间维度：改动包进 effect
    const dispose = ctx.tools.register(myTool)
    return dispose                         // 交回后悔药
  })
}
```

![三层结构](https://img.riba2534.cn/images/2026/08/dsh-theseus-02-layers.png)

*定理在最下面，Cordis 把定理变成 API，dsh 是搭在 API 上的产品。现在看的是中间这层。*

`ctx.effect` 是整个框架唯一的改动入口：注册事件监听是它的包装，发布服务是它的包装，挂载子插件还是它的包装。正因为入口唯一，"任何经过 ctx 干的事都会在卸载时被自动撤销"才从愿望变成了结构。更顺手的写法是生成器：每做完一步初始化，就把这一步的撤销函数 `yield` 出去当场登记，再接着往下建。中途失败时，已经登记的撤销函数照样执行，建到一半的资源不会漏网。

`inject` 声明的依赖由一个状态机兑现：依赖没到齐，插件停在等待态；到齐了自动加载；提供方换了个实例，依赖它的插件级联重启。热重载是同一套机制的自然结果：改了某个插件的源码，框架把旧实例的效应撤干净，加载新代码重新来一遍，进程里其他部分毫发无损，开发者也无需在代码里标注任何"热更新边界"，而 Webpack 和 Vite 的 HMR 都要求手写接受边界。

## 前人走过的路

同一个问题上，别人走过几条路。

空间那一侧最接近的先例是 OSGi 的声明式服务：组件声明提供什么、需要什么，框架按可用性协调激活，思路与反应式协效应一脉相承。差别在清理上，OSGi 的回调靠手写，资源安全押在开发者的自觉上。

Erlang OTP 的热更新走另一条路：新旧代码并存，靠一个手写的状态迁移函数把旧状态搬进新代码。能力很强，代价是每次升级都要人来写迁移逻辑。

前端世界的 React `useEffect` 离"效应与撤销配对"的形态最近，注册时返回清理函数，卸载时自动执行。局限在于 hook 只能写在组件顶层，进不了条件和循环，效应无法从别的效应组装出来，也就谈不上自动推导复合的撤销。

Cordis 的取舍放在对照里看得清楚：内存状态一律撤销重放，换来的是迁移函数彻底消失；效应可以任意组装嵌套，复合的撤销自动推导。组件自身的内存状态不跨重载存活，除非托付给一个更长命的依赖，这一点与热更新方案相比是明确的短板。

dsh 对 Cordis 的取舍还要再进一步：源码被整个收进了 dsh 自己家里，版本钉死，每一处与上游的偏离都登记在案，没有走"引用一个外部依赖"的寻常路。理由是 harness 的正确性建立在框架内部行为的确切语义上，生命周期、撤销顺序、依赖协调，这些语义必须完全受控。登记的本地修改里有一批是生命周期加固，修的都是"卸载过程中又发生了卸载"这类重入竞态。

## 主循环也只是一行配置

到 dsh 自己了。它在 Cordis 之上给自己立了几条规矩：模型看得见的必须能从会话日志重建；注册必须交回撤销；能力必须三个角色齐全；配置错了必须大声失败。落到架构上，一个词概括：不留内核。

几乎每个 agent 框架都有一块碰不得的核心，通常就是主循环。dsh 的架构文档里写着："There is no privileged core to patch"。这句话可以直接拿配置文件验证。dsh 的基础组合就是一份插件清单，节选几行：

```yaml
- id: session      # '@deepseek-ai/dsh-session'      会话日志
- id: tools        # '@deepseek-ai/dsh-tools'        工具注册表
- id: llm          # '@deepseek-ai/dsh-llm'          模型运行时
- id: agent-loop   # '@deepseek-ai/dsh-agent-loop'   主循环，也是插件
- id: tool-bash    # '@deepseek-ai/dsh-tool-bash'    bash 工具
```

主循环和 bash 工具在同一张清单里平级排列，谁也不比谁特殊。这份出厂配置的头注释里躺着一句自我说明："Row order carries no load semantics"，行的顺序不携带任何加载语义，分组只是为了给人读。想换一个完全不同的循环实现？换掉那一行。

![没有中心的环](https://img.riba2534.cn/images/2026/08/dsh-theseus-06-ring.png)

*环上没有中心，心跳也只是环上的一员。*

架构文档的末尾有一张"你想干什么 → 挂哪个扩展点"的对照表，二十来行覆盖了加模型、加工具、拦截请求、改上下文这些常见需求，而它旁边写着：要改循环本身，就得同时改这张表。这比任何抽象论证都更能说明"不留内核"是当真的。

## 同一份清单叠出不同产品

把清单摊开，就是 dsh 的全貌。中间一层是几十个能力插件，除了前面见过的会话、工具、模型三行，还有文件系统、shell、终端、子 agent、技能、沙箱、审批、联网搜索，每一个都占清单里的一行，主循环混在其中毫无特权。它们脚下是 Cordis 运行时，管上下文、效应追踪和依赖协调。头顶是产品形态：无头命令行、Web 界面、给编辑器和自动化用的 ACP 通道、给程序调用的 SDK。运行时这一层之上其实还有一整套生成式 RPC 和浏览器端插件树，这里不展开。

![dsh 整体分层架构](https://img.riba2534.cn/images/2026/08/dsh-theseus-11-overview.png)

*前面那张三层图分的是理论、框架、产品；这张把最上面那格拆开：同一批插件踩着 Cordis 运行时，撑起头顶的产品形态，装哪些由补丁层决定。*

组装方式走得更远。dsh 进程启动时的根配置是个空数组，每次启动都被重写归零；完整的插件树靠一层层补丁叠出来：基础层给出全部核心插件，产品层（无头模式、Web 模式）各自叠一小层改动，用户偏好又有两层，每个 profile 一层、机器全局一层，命令行还能再压一层临时补丁。每层只描述"改什么"。想知道一次启动到底装了什么，`dsh --dump-config` 会把叠完的整棵树打印出来，每段标注它来自哪一层。

这种玩法的底气直接来自 Confluence 定理：最终状态只由叠完的清单决定，与叠的过程无关。补丁层之间有顺序，插件行之间没有加载顺序，激活时机完全由依赖满足关系驱动。某个插件依赖的服务晚到了，它就停在等待态，服务一到自己起来。写配置的人从头到尾没管过"谁先启动"。

## 一次对话走过的路

那一行 `agent-loop` 展开之后是什么样子？循环本身是全项目最普通的部分，体量小得跟它的地位完全不相称。所有 agent 产品的循环都长一个样：

```text
收到输入 → 组装提示词 → 请求模型 → 模型要调工具吗？
   ↑                                    ↓ 要
   └─────── 把工具结果喂回去 ←──────────┘
```

结构上是两层嵌套。一个回合（turn）从领取输入开始，到不欠任何工作结束；回合里每次模型请求加上它引发的工具调用，是一个步骤（step）。外部输入一律进收件箱，三种投递方式的差别只在时机：

| 动作 | 何时处理 | 是否叫醒循环 |
|---|---|---|
| followup | 下一个回合 | 叫醒 |
| steer | 下一个步骤 | 叫醒 |
| inject | 下一个步骤 | 不叫醒 |

领取动作发生在每个步骤开始之前，之后到达的消息只能等下一步。哪怕这一步被某个关口整个拒绝，回合照样合法关闭，尝试本身也留在记录里。

把一个步骤放大，能看到完整的数据流。从收件箱领取消息后，先组装系统提示词；对话历史不从内存里拿，从会话日志（session log）现推。这份日志是一条只追加的事件流，会话里发生的每件事都按序记录在上面。请求发给模型，流式返回的每个片段边到边写入日志；模型要调工具，工具走完自己的管线，结果同样写入日志，再进入下一个步骤。每个环节都在读日志或写日志，没有第二份状态。

![一次对话的数据流](https://img.riba2534.cn/images/2026/08/dsh-theseus-12-turnflow.png)

*每个阶段都把事件写进日志，只有推导历史这一步从日志往回读。*

循环的每个关键节点都是一个事件，但事件分四种派发方式，各有语义承诺。拦截型的关口是一条链，每个监听器处理完要显式放行，可以改写也可以整个否决，这样的关口在步骤开始前、模型请求发出前、工具执行前后各有一个；有序检查点挨个执行，没有放行一说；落盘这类"每个监听器都必须有独立机会"的时刻并行派发；剩下的纯通知发出去就不管。

划界还有一条成文规则：持久的事实进日志，活体的拦截走事件，所以回合和步骤的边界只在日志里存在一份，故意没有镜像事件。给循环加任何新行为，标准姿势都是挑对派发方式挂插件，没有一种需要动循环本身。Claude Code 生态的 shell 钩子协议能被一个普通插件翻译过来，翻译过去的每一个钩子都落在现成的关口上，桥没有为自己新开任何关口，也没动循环一行。

上面一笔带过的"组装系统提示词"，本身也走注册制。系统提示词由各插件注册的片段按序号拼接：身份说明排最前，部署方的人设居中，各工具的使用指导靠后，同名片段近层覆盖远层。会随时间变化的动态上下文走另一条通道，被物化成一条普通的用户消息落进日志，而且只在内容真正变化时才重发一次。服务商是按请求前缀命中缓存的，动态内容每轮换位置会让前缀失配，这条通道既保住了"模型看到的都有记录"，又不打断缓存。

## 工具执行的三道关

上一节说循环在工具执行前后各留了一个关口。把工具这一段单独放大：前后两个关口，加上执行本身，是三道关。模型说"我要跑一条命令"，命令要依次穿过它们。

第一道关在执行前，回答"该不该跑"。审批本身是一种独立能力，需要人点头的调用在这里一次性提问，没人应答就按拒绝处理；守卫的返回类型只有"拒绝理由"，没有"放行"，所以无论多少条守卫排成什么顺序，都无法把一次拒绝翻成许可。提示词里看不见某个工具，也不等于它不会被执行：被禁用的工具在执行时还会再拒绝一次，提示词过滤和执行拒绝查的是同一张可见性表，不存在绕过提示词就能用的后门。调用本身在执行之前就已写入日志，被拒绝的调用照样有记录。

第二道关是执行本身，回答"怎么跑"。沙箱策略在这里生效，dsh 内置三档：只读、工作区可写、完全放开，Linux 上由 bwrap 或内核的 Landlock 兜底强制。超时插件在这一层包计时器，预算来自工具自己的声明。

第三道关在执行后，决定模型看到什么。超大的输出被截断收存，模型只拿到摘要和取回位置；同一个调用原样重复到阈值时，这一步的工具结果后面会跟上一条提醒消息，结果本身一字不改，留给审计。走完三道关，结果写入日志，回到循环。

![工具执行管线](https://img.riba2534.cn/images/2026/08/dsh-theseus-13-toolgates.png)

*三道关里只有第一道能把调用整个拦下，后两道改变的是它怎么跑、以及模型最后读到什么。*

调度层面另有保序规则。模型一口气发出五个工具调用时，标记为并发安全的部分允许重叠执行，但策略检查、结果提交、结果进入上下文三件事严格保持模型给出的顺序。已经启动的调用在中断时会被完整等完再提交；没来得及启动的补一条"未派发即中止"的记录，保证日志里调用与结果永远成对。并发安全的判定是保守的：工具没有明说"我安全"，一律按独占处理。后来加的 Code Mode 允许模型直接写程序批量调工具，程序里的每个子调用照样一个不落地过这三道关、照样写入日志，原则没有为它开例外。

回头看会发现，这一整层策略结构和前面那条交换性判据是同一件事。守卫只能拒绝不能放行，工具限制按交集组合，可见性与可执行性共用一张表，于是策略的组合结果与注册顺序无关。理论说可交换的表落在安全区里，dsh 就把自己的策略层刻意做成了这样的表。

## 日志即真相

dsh 有一块理论层没有覆盖的原创设计，它回答的问题是：模型的对话历史放哪？

直觉的做法是内存里放一个 messages 数组，随用随改。隐患跟着来：某个插件悄悄往数组里塞了一条上下文，另一个插件改了历史消息，事后却没有任何记录可查。等到需要复盘"模型当时到底看到了什么"，谁也说不清。

dsh 的做法叫事件溯源（event sourcing）：会话是一条只追加的事件日志，每个事件按序写入，用户消息、模型输出的每个片段、每次工具调用和结果、回合与步骤的边界、上下文的每次注入，全部在内。要调模型时，从日志推导出消息列表发出去。**会话日志是唯一的真相；消息历史只是它的推导结果，每次现算。**

配套的铁律叫 "Model-visible ⟺ logged"：凡是模型看得见的内容，必须能从日志逐字节重建。重建的对象不只是消息，还包括随请求写入日志的头部快照：用的哪个模型、渲染后的系统提示词、当时的工具表。这条铁律配有一个专职的核对插件，在请求真正发出的那一刻，把冻结的请求与从日志重新折叠出的消息和请求头逐字段比对，对不上当场报错。缓存不能给自己作证。

这个核对插件没有进产品的默认装配，日常核对发生在测试与显式开启的组合里。产品树上依靠的是构造层面的保证：消息列表的唯一来源就是日志推导，想绕过都没有第二条路可走。

模型看到的那份历史，本身也只是日志的一个投影。界面上的完整对话是另一个投影：同一段被摘要遮盖的历史，模型的投影里消失了，界面的投影里还在，而这不需要两份存储。顺着数下去，投影还有一串。

![一份日志，多个投影](https://img.riba2534.cn/images/2026/08/dsh-theseus-14-projections.png)

*同一条只追加的流，派生出模型视野、完整对话、分叉、状态、遥测和回放夹具；被遮盖的区间只在模型视野里消失。*

进程崩了日志还在，重放一遍就恢复。

想从第 37 步分出一个平行世界试另一条路，从日志切一刀就是分叉。

回归测试不再需要 API key。录一次真实运行的日志，以后拿它当剧本回放整个应用，dsh 的快照测试夹具用的正是产品自己吐出的日志文件。

发给模型的请求永远是上一次的前缀加一段尾巴。这不是刻意优化出来的：历史只能追加，投影是纯函数，请求形态被结构逼成了这样，服务商的 KV 缓存因此持续命中，省下的是推理账单上直接看得见的钱。

出了事故，日志就是完整证据链。遥测搭的也是这趟车，对外上报的运行记录与日志一一对应，接收方拿事件序号去重，序号出现缺口是常态，从来算不上事故信号。

连"压缩历史"都没有破例。对话太长需要摘要时，旧事件一条不删，新写一条"从第 X 条到第 Y 条被这条摘要遮盖"的记录，推导消息时自动跳过被遮盖的区间。压缩来临前，还会先把历史里过胖的工具结果就地修剪一遍，再决定要不要摘要。生成摘要的那次调用逐字复用会话自己的提示词前缀，把压缩指令追加在最后，于是同样命中缓存。

进程死在一个回合中间怎么办？重启后那些已经写入日志的半截事件一条不删，补一条"被中断"的收尾把回合合法关闭，再给没等到结果的工具调用补上错误记录，日志重新变得完整。

格式演进同样有防呆设计：格式版本号是一个单调整数，是否升级由写入方判断，判断标准只有一条，旧运行时读了会不会悄悄错。读到不认识的事件类型时默认拒绝整份日志，除非那条记录自带"可忽略"标记。宁可拒绝一份读不懂的日志，也不静默吞掉可能改变语义的内容。

体积问题被留在物理层解决。模型输出的流式片段逐条写入会让存储文件膨胀几十倍，存储层把连续片段无损打包成行，实测能把真实编码会话的日志缩小约六成；这之上还叠着一层默认开启的压缩。语义层的事件一条没丢，压缩只发生在存储层。

dsh 里很多看似独立的功能，其实都是会话日志的衍生品。计划模式是日志里的一条状态记录，恢复会话时自然还原；待办清单的当前状态就是最后一条清单记录，重放到哪一条，清单就是哪一版；技能目录的更新也走日志，只有摘要真正变化时才追加一份新目录。同一个模式在系统里反复出现：状态在日志里只记一份，其余全是投影。

## 一种能力，三个角色

dsh 里每一种能力，执行命令、读写文件、调模型、开子 agent，都按同一个模子拆成三个角色：

| 角色 | 职责 | 以 shell 能力为例 |
|---|---|---|
| 服务定义 | 说清这个能力"是什么" | 三个方法：解析请求、执行、启动进程 |
| 服务提供方 | 具体怎么干 | 按 shell 方言和是否套沙箱，各有一套实现 |
| 消费方 | 把能力暴露给模型 | bash 工具，只认服务定义 |

![一个接口，可换的供方](https://img.riba2534.cn/images/2026/08/dsh-theseus-08-seam.png)

*中间那格不动，两边各自替换。*

为什么拆三份？三者的变化速度不一样。定义轻易不动，实现经常换，模型看到的工具接口必须稳定。拆开之后，换实现就成了改一行配置的事。仓库里有个专门的概念验证：把文件系统和进程两个提供方换成 E2B 云沙箱的实现，上层的 bash 工具、持久终端、语言服务器一行代码没改，整体跑到了云端。跑到远端甚至不需要新的 shell 实现，换掉底下的进程提供方就够了。

反应式协效应在这一层兑现。换一个模型提供方，注册表的路由替换是原子的，候选集先整体校验，有一个不合格就整体不动，避免旧的撤了、新的没上的空窗；换掉整个实现包，依赖它的插件自动级联重启，其余部分原地不动。

这个模子里还有几条死规矩。默认值必须显式：请求进来先经过一个明确的解析步骤，把所有可选项落成确定值，执行环节拿到的永远是全量事实，禁止在执行函数里随手写兜底默认值。它防的是两个调用路径各自兜了不同底这类最难查的 bug。

配置错误的处理，网页搜索是个典型例子。选择用哪个搜索提供方时，所有情形被穷举成一张表：点名的提供方不存在、点名了但当前不可用、一个可用的都没有、多个可用却没点名，每种失败各有一个带名字的错误码，各走各的路径，错误消息里直接列出所有可选项。翻遍这段逻辑找不到一条静默兜底的路。这条规矩有自己的名字：misconfiguration fails loud，配错了就大声失败。

## 一船多面

配置能换掉的不只是实现。同一个 dsh 进程可以同时载着装备完全不同的多个 agent，机制叫 preset。每个会话可以选一份"人格清单"，决定这个 agent 看到哪些工具、用什么提示词。可以配一份只读审计用的 preset，关掉全部写文件工具，甚至在隔离域里换上自己的文件系统提供方遮蔽宿主那份；同一进程里旁边的开发 preset 完全不受影响。

底下是一层可嵌套的作用域，两个方向刻意不对称：注册的可见性沿父子链向下继承，agent 看得见自己 preset 层的注册，preset 层看得见全局层，近者覆盖远者；事件的可见性向上传播，挂在父层的监听器收得到子孙的事件，反过来不行。一份 preset 全进程只挂载一次，选它的会话认它作父即可加入。这层作用域管的是可见性和生命周期，设计记录里专门写明它不是权限边界，授权另有各自的机制把守。

子 agent 也是同一个模子的产物。委派能力拆成三角色之后，提供方可以同时注册六种：进程内的新会话、当前会话的分叉、两种独立子进程，甚至一次跑在 Claude Code 或 Codex 里的回合。对模型而言全是同一个"派活"工具，产品间互操作被降格成了又一次提供方替换。

把这几层放在一起看：补丁层决定进程里装哪些插件，preset 决定每个会话看到其中的哪一部分，提供方注册决定每种能力由谁来干。三处都不用改代码，改的都是配置文件里的行。产品形态、agent 人格、执行后端，在 dsh 里落在同一种介质上。

## 船员自己换船板

回到最初的问题：船上的水手自己换船板，怎样才安全？

dsh 给模型开了七个工具，按用途分三组。查看组三个，从列出可探查的入口，到按名字查一个服务的完整接口，再到看自己会话名下定义过什么。定义组一个：提交一段新插件代码，系统做语法检查后记录在案，什么都不执行。运行组三个：挂载、停止、遗忘。

查看组背后是一套反射机制。模型读到的服务接口来自编译期从源码提取的目录，与人类文档是同一个扫描器的两份产物，谁先漂移谁在 CI 上红；哪些服务正在运行则来自进程的实时状态。两相求交，报告同时反映代码定义和进程现状。目录经过刻意裁剪：动态插件够不到的服务键（启动器注入的引导值、浏览器侧的服务）不会出现在里面，免得模型照着调一个永远拿不到的东西。

![水手在自己的甲板上换板](https://img.riba2534.cn/images/2026/08/dsh-theseus-09-selfrepair.png)

*水手在自己站着的甲板上换板，拆下的每块板都带着标签。*

安全依靠几层互相独立的设计。定义与运行分离，写错的代码在获得编号之前就被语法检查拦下，所有副作用都被推迟到运行环节。涉及浏览器端的挂载必须由人在界面上批准，没有超时自动放行这回事。

停止一个动态插件时，效应系统兑现前文的承诺，它注册过的工具、挂过的监听、发布过的服务照着后悔药清单逐一撤销，进程里其他部分不受波及。前面那条"最终状态只看当前清单"的定理，在这里是模型每一次试错的兜底。日志没有为动态插件单开事件，挂载和卸载就是普通的工具调用记录，所以重启后的进程干干净净，一张指向已消失定义的卡片会如实显示失效，绝无"看起来还能跑"的假象。

隔离用的 vm 沙箱挡不住有心人，这套工具的威力等同于 bash 权限，仓库文档明明白白让使用者按这个级别对待。换板这件事，没有一条绕过审批的路。

## 理论管不到的地方

泼出去的水收不回。跨越系统边界的操作分成两段：获取阶段，比如打开文件、申请内存，留在边界内，可以撤销；发射阶段，比如写出去的字节、发出去的网络包，越过边界落在别人地盘上，撤不回来。Confluence 定理只谈系统内的状态，对发射出去的东西无能为力。既然日志这种"发射"收不回，dsh 干脆让它升格为唯一真相，一切内部状态反过来从它推导。

后悔药的药效没人验证。运行时忠实地攒下每张撤销函数，但"这个撤销真能恢复那个效果"是插件作者的义务，框架不检查。

环形依赖会让相关插件集体趴窝。好消息是这种局面从依赖声明就能算出来，加载时即可报告，与并发死锁那种跑起来才知道的性质完全不同；坏消息是解开环要把双向交互拆成更多单向组件，最坏情况下组件数量平方级增长，配置和认知成本都跟着涨。

还有人这一侧的代价。拦截链里一个监听器忘了显式放行，整条链后面的全部静默失联；三角色拆分让每种能力各司其职，同时也意味着复杂度守恒，它从中心循环挪进了协议、所有权和装配关系，学习曲线实打实地陡。dsh 上线才两个月，日志格式版本号至今钉在 0 上，还没经历过一次真实的格式演进，能不能扛住真实世界的自演化频率，要留给时间回答。

## 造船的也是 agent

最后一层设计藏在开发流程里。仓库的决策记录里有一段话：

> This codebase is developed primarily by coding agents. Agents follow enforced gates far more reliably than prose conventions.

这个代码库主要由 coding agent 开发，两个月上万次提交的速度佐证了这一点。整套工程纪律因此长成了另一副模样：写给人看的规范靠自觉，写给 agent 看的规范必须是会报错的命令。项目里躺着几十个校验脚本，从"每个导出必须有文档注释"到"文档里粘贴的类型声明必须与源码保持一致"，全部接入 CI，违反一条就红。

![船厂与检查门](https://img.riba2534.cn/images/2026/08/dsh-theseus-10-shipyard.png)

*船厂里的工人也是机器人，每段船体都要过检查门。*

决策记录制度也是为 agent 设计的。每个非平凡的架构决策都要留档，并且强制写明当时否决了哪些备选方案，理由直白：没有记录败者的决策，迟早被翻案重议。归档的决策永久冻结，连格式都有校验脚本把守。

档案自身也有生命周期：提议、落地、否决三种状态直接编码在目录路径里；落地的记录随代码演进同步更新路径与名字这类事实，永不改写当年的决策本身；推翻旧决策要写新档案并互相链接。连文档的篇幅都有预算门禁，超过字数上限就构建失败，逼着作者在添加内容的那一刻想清楚它真正的归属。

真实 API 的测试不许省着用（"We are DeepSeek — do not ration real-API tests"）；快照测试的夹具直接取自产品自己持久化的日志文件，同一个文件既是回放的输入，又是行为的期望输出，手写 mock 在这套体系里没有位置。

这套纪律有一笔学费背书。仓库的事故复盘里记着一次翻车：某次改动后 178 个测试全绿、行覆盖率 100%，真实客户端一连上就崩。原因是插件源码里多写了一行 `export default`，框架的模块解包会优先取 default 导出，把同级具名导出的依赖声明整个扔掉；而所有测试都手工挂载插件，没有一个走过真实的加载路径。此后立下的规矩：测试必须走真实的组装路径；覆盖率证明的仅仅是代码跑过；没盖住的代码行往往该删，补测试反倒是次选。

于是出现了一幅自指的画面：一群 agent，在一套防 agent 犯错的门禁下，建造一个供 agent 运行、并允许 agent 改造自己的系统。船厂里的工人和船上的水手，是同一种人。

## 船还是那条船吗

回到普鲁塔克。换完所有木板的船还是原来那条吗？哲学家吵了两千年。这个仓库把身份的判据挪到了那本随船的航海日志上：只要日志还连续，船就还是那条船。

木板尽管换。dsh 把这道辩题写成了可以执行的代码。

这条船最终能驶多远，两个月的航程还看不出来。OSGi 和 Erlang 早就在各自的领域里换过板，dsh 的位置在于把这套工艺搬进了 agent harness，并且把锤子递给了船上的水手。
