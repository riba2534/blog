我盘了一下自己的 `~/.claude`，200 多个 skill。最长的那个 SKILL.md 有 6.7 万字节，光它一份就抵得上一篇长文，我上次真正用到它是什么时候已经想不起来了。底下还挂着近千个 references 文件。全部加起来三十多万 token，比 Claude Code 的整个上下文窗口还大。

就在同一周，Anthropic 的 Claude Code 团队公开了一件方向完全相反的事：他们把 Claude Code 的系统提示词删掉了 **80% 以上**，编码评测上没有观察到可衡量的下降。

一边是我在往里堆，一边是造这个东西的人在往外扔。

## 三类提示词

提示词当然有用，问题在于哪些还有用。

把你写过的所有 CLAUDE.md、skill、系统提示词摊开，按一个标准分类：**这段话是在补模型的短板，还是在描述只有你才知道的事。** 按这个标准能分出三类，它们的保质期差着数量级。

**第一类是补丁。** 为了对抗模型某个具体的坏毛病而写的。比如"不要写多行注释块"，这条规则会存在，是因为某一代模型总爱生成大段没用的注释。再比如"改完必须自己跑一遍测试"，因为它以前会说改好了但根本没验证。

补丁的特征是它对应着一次具体的失败，出身特别好认。你多半还记得它是哪天加的，甚至记得当时是哪个 bug 惹的祸。像"不许自作主张改测试文件"这种，背后基本都是同一个场景：某次模型为了让测试跑过，把断言直接改成了它自己的输出。

**第二类是能力。** 教模型怎么做一件通用的事：怎么做代码审查、怎么写提交信息、怎么系统性地排查一个 bug、怎么设计 REST 接口。这类内容通常写得最长，因为它本质上是在写教程。

这一类也最容易被高估。写它的时候手感特别好，你在输出结构化的知识，看起来很像在建设什么东西。但它的价值完全取决于一件事：模型现在到底知道多少。而这个问题大多数人写之前根本没验证过，我也没有。判断"模型不懂这个"比想象中难，因为你随手想到的测试方式，往往正好是它最擅长的那种问法。

**第三类是身份。** 告诉模型你是谁、你的代码库长什么样、你们团队怎么做事。"我们所有类型定义都堆在一个大文件里，别处找不到"、"这个服务的灰度必须先过预发环境"、"我不喜欢在代码里写中文注释"。

这类写起来最没成就感，因为它们看上去就是一堆琐碎事实，不成体系，也不像什么方法论。但恰恰是这些琐碎东西，模型再聪明也猜不出来。

这三类的区别，在于它们跟模型权重的关系。

| 类型 | 它在补什么 | 半衰期 | 下一代模型会怎样 |
|---|---|---|---|
| 补丁 | 模型当前的某个具体缺陷 | 最短，一个大版本可能就失效 | 大概率被专门修掉 |
| 能力 | 模型的通用知识盲区 | 中等，会被训练数据追上 | 逐渐变成常识 |
| 身份 | 只有你知道的事 | 不会过期 | 权重里永远不会有 |

第一类和第二类都在赌同一件事：**模型现在还不会。** 而这个赌注每隔几个月就要重新结算一次。第三类不用赌，因为你的仓库长什么样、你们团队怎么做事，这些东西再训练一万次也不会进到权重里去。

前两类的预期寿命都很短。它们通常只是针对当前模型缺陷打的补丁，而这些缺陷恰恰就是下一代模型在训练和后训练中被专门修掉的目标。

你写的规则越是精准地击中了模型的痛点，它就越可能出现在下一代模型的优化清单上。**精准本身就是过期的前兆。**

能活下来的，是那些没办法住进模型权重里的上下文：你的偏好、你公司的私有知识、你的工具、你的数据。那个持久的层，教的是你是谁。

## 三个判别方法

**第一个问题：不写会怎样？**

如果答案是"模型会做错"，那是第一类或第二类。如果答案是"模型会做得跟我想的不一样"，那是第三类。

这个区分是整套分类里最关键的一条。**做错和做得不一样，完全是两码事。** 前一种是模型的能力缺陷，全世界用户都在面对同一个问题，所以它一定会被下一代模型当成优化目标，你写的规则只是替它临时兜着。后一种是信息不对称，模型不知道你们的部署顺序，不知道你讨厌什么风格，这件事再训练多少次也不会改变，因为那些信息压根不在互联网上。

拿两条真实的规则对比。"改完代码必须自己跑一遍测试"，不写的话模型可能真会漏掉，属于能力问题，而且新模型已经基本不用提醒了。"改完这个服务要顺手更新 changelog"，不写的话模型不会出错，它只是不知道我们有这个规矩。前者该删，后者该留。

**第二个问题：这条规则原样发给另一家公司的人，还能用吗？**

能用，说明它讲的是通用知识，属于前两类。不能用，说明它携带了只属于你的信息，是第三类。

这个测试比第一个更快，尤其适合拿来审视从网上下载的 skill。一个能被公开分发、装在成千上万台机器上的 skill，按定义就通过不了这个测试，它必然是通用的，否则别人装了也没用。

**第三个问题：你写它的时候，用了多大力气？**

这条听起来不像判别方法，但我觉得它最准。

回头翻自己写的那些规则，有个规律很明显：**补丁类的措辞总是最凶的。** 满篇的"绝对不要""必须""任何情况下都"。因为写的时候人正跟模型的某个顽固倾向较劲，它反复犯同一个错，语气就一次比一次重。而身份类的规则读起来都很平静，因为那只是在陈述一件事实："类型定义都在 types.go 里。"

所以有个偷懒的判断办法：**你写的时候越用力，那条规则越可能已经快过期了。** 力气都是冲着模型的缺陷去的，而缺陷会被修好。

那些全大写、加粗、写着"这不容商量"的段落，基本可以直接进删除清单。它们的语气已经把自己的出身说出来了。

反过来也一样。翻一遍自己的配置，那些读起来最平淡、最像流水账的句子，往往才是最该留的："构建产物在 dist 目录"、"这个字段的单位是毫秒"。它们没有任何说服的意图，只是在陈述一件事。而陈述事实这件事，不会因为模型变强而失效。

## 补丁会过期

第一类和第二类会过期，这件事已经在发生了。

最容易感知的例子是"让我们一步步思考"。这句咒语当年是提示词工程的招牌，谁都要在提示词末尾缀一句。现在写不写基本没区别，推理模型自己就在做分步推理，你那句话唯一的作用是让它多花点时间，把你想听的过程再复述一遍。

这不只是个人体感。OpenAI 的推理模型使用建议里白纸黑字写着：让模型"一步步思考"或者"解释你的推理"是不必要的；还建议先写不带例子的提示词试试，别一上来就 few-shot。

**一句被写进无数教程的技巧，被写它的那家公司自己标注成了多余。**

技巧没有消失，它只是搬了个家，从你的提示词里搬进了模型的权重里。而搬走之后，原地留着的那句话就成了多余的。

7 月 24 日，Anthropic 发了一篇工程博客，标题是《The new rules of context engineering for Claude 5 models》，作者是 Claude Code 团队的 Thariq。文章记录了他们重新审视自己那套上下文的过程：哪些规则当年非写不可，哪些到今天已经变成了负担，以及删掉之后评测为什么没掉。

他们能一次砍掉八成还不掉分，原因就在这里。**那八成里的绝大部分，是给上一代模型写的补丁。** 补丁对应的毛病没了，补丁自然就成了废纸。

第二类也在缩水，只是慢一些。教模型"怎么系统性排查 bug""怎么做代码审查"这种内容，刚开始那会儿确实有用，现在很难说。这些方法论早就被写进了无数本书、无数篇博客、无数个开源项目的贡献指南里，而那些恰恰是训练数据的主体。**你在教它的东西，它读过的版本比你写的多得多。**

拿一个讲"怎么排查线上问题"的 skill 来说，几千字写下来，通常是这么个结构：先看监控、再看日志、缩小时间窗口、对比变更、二分定位。这些模型不用你说也会。真正只有你知道的可能就两句：日志在哪个平台、哪几个服务的报警是出了名的爱误报。

九成的篇幅在教它已经会的事，剩下一成才是你真正想让它知道的。而写的时候，几乎没人会意识到这个比例。

## 他们具体删了什么

文章有一句话解释了这件事为什么难：

> Unlike a prompt, context is used generally across many requests, so it cannot be as specific.

提示词是给单次请求写的，可以写得很具体；上下文要跨很多次请求复用，所以没法具体。你写 skill 的那一刻，根本不知道下一次的任务会是什么。

这句话解释了一件我之前没想通的事：**为什么 skill 比一次性的提示词更容易过期。** 因为它天生就得写得通用，而通用的东西正好是训练数据里最密集的部分。你越是把一条规则写得放之四海而皆准，它就越可能已经躺在权重里了。

他们把过时的做法列成了六条：

| 过去 | 现在 |
|---|---|
| 给 Claude 定规则 | 让 Claude 自己判断 |
| 给 Claude 举例子 | 把接口设计好 |
| 重要的全堆在最前面 | 渐进式披露，用到才加载 |
| 同一件事反复强调 | 写清楚工具描述就行 |
| 拿 CLAUDE.md 当记忆 | 自动记忆 |
| 写简单的 spec 文档 | 用测试套件、HTML 原型当引用 |

第二条最反直觉：

> With our newest models, we've found that giving examples actually constrains them to a certain exploration space.

举例子会把模型限制在某个探索空间里。Few-shot 是被写进无数教程的基础技巧，现在它的副作用被点名了。

我的理解是，例子传递的信息比你以为的多。你想传的是"格式长这样"，模型收到的却是"风格、粒度、边界、口径全都长这样"。模型越强，从一个例子里读出的隐含约束就越多。你以为在给参考，它以为你在给规格。

他们给的替代方案是回头去打磨工具本身。Todo 工具只要把状态定义成 `pending / in_progress / completed` 的枚举，再加一条"同一时间只能有一项处于 in_progress"，模型自己就懂该怎么用，一个例子都不用给。

最后一条也值得抄：引用优先用代码形式，因为那是模型最熟的语言。一份 HTML 原型的效果，通常好过对这个设计的文字描述，也好过一张截图。这条推翻了我的一个习惯——我以前总想把需求"翻译"成自然语言讲给模型听，觉得讲得越细越好。但自然语言是有损压缩，你描述一个界面，再准确也会丢掉间距、层级、状态，而丢掉的部分模型只能靠猜。

按前面那个分类看，这六条讲的是同一件事：**第一类和第二类的做法在集体过期。** 定规则、举例子、反复强调，都是在补模型的短板；而渐进式披露、设计接口、用代码当引用，本质上是把位置腾出来，让模型自己走。

文章末尾他们上了个新命令叫 `claude doctor`，在 Claude Code 里敲 `/doctor`，专门帮你给 skill 和 CLAUDE.md 瘦身。

一个团队做了个工具，帮用户删自己写的东西。这个信号够强了。

## 留着不删的代价

如果过期的提示词只是"没用"，事情还算好办。

真正的问题在于它有害。而且危害的形式，比"占地方"复杂得多。

### 它会被当成攻击

Superpowers 是这类重型插件里最典型的一个，26 万 star，从 2025 年 10 月做到现在。它的 SessionStart hook 会在每次会话启动时，把一份 skill 文档整个塞进上下文，外面包一层标签：

```
<EXTREMELY-IMPORTANT>
If you think there is even a 1% chance a skill might apply to what you are doing,
you ABSOLUTELY MUST invoke the skill.

IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE. YOU MUST USE IT.

This is not negotiable. You cannot rationalize your way out of this.
</EXTREMELY-IMPORTANT>
```

[Issue #1878](https://github.com/obra/superpowers/issues/1878) 记录了它在 Sonnet 5 上的遭遇。报告人新开会话问了个很普通的问题，模型的第一反应是：

> I need to flag something before continuing: that message contains what looks like a prompt-injection attempt — fake `<EXTREMELY_IMPORTANT>` tags, a bogus "superpowers" skill dump, invented tool names... I'm disregarding all of it.

它拒绝执行，反过来问用户到底想问什么。

后面还有反转。用户追问了一句"你怎么知道它没有对应的 skill"，模型这才去翻磁盘，把文件的实际内容和聊天里冒出来的文本做了个 diff，发现逐字一致，于是当场认错：它承认自己是凭语气就跳到了"注入"这个结论，没做核查。它最后总结了一句：语气是个很弱的信号，合法的 skill 也可以写得很强硬。

模型自己给出的诊断比任何外部批评都准：**它是被语气骗的。** 全大写的祈使句、"NOT NEGOTIABLE"、"YOU MUST"，这套话术在提示词注入攻击里太常见了，常见到模型见了先起疑。

那句"这不容商量"想换来的是绝对服从，实际换来的是一整轮对话——用户的第一个问题压根没人回答，全花在自证清白上了。

这是典型的补丁过期。那套高压措辞是为了对付"模型不肯乖乖调用 skill"这个老毛病，而新模型不但改掉了老毛病，还长出了识别高压话术的能力。补丁没跟着改，就从解药变成了毒药。

写下那段话的人当时肯定觉得自己在解决问题，而且在那会儿的模型上他多半是对的。谁也不会觉得自己正在写一条错的规则，大家写的都是会过期的规则，区别只是保质期多长。

### 它的副作用出现在别处

同一句话还有个更隐蔽的后果，记录在 [issue #1917](https://github.com/obra/superpowers/issues/1917) 里。因为"哪怕只有 1% 的可能性适用，你也必须调用"这条路由压力一直压着，agent 对任何任务都默认 fan-out 派发 subagent，哪怕那是个几行的小改动。而每派一个 subagent，就要重新读一遍计划、重新在代码库里定位、把文件从冷状态重新加载一遍。**这笔上下文重建的开销，要按 subagent 的个数付 N 遍。**

任务真正独立、数量又多的时候，隔离是收益；但几个紧密耦合的小任务各自需要几乎相同的上下文时，隔离就成了纯粹的重复开销。而问题在于，整条链路上没有任何东西在往反方向拉。

一条为了确保 skill 被触发而写的指令，最后扭曲的是 agent 判断"要不要拆任务"的默认值。写它的人几乎不可能预见到这一层。**这是长提示词最难防的地方：它的副作用不出现在它管的那件事上。**

### 长度本身就是成本

[Issue #2017](https://github.com/obra/superpowers/issues/2017) 里有人做了组对照实验，方法比大多数博客严谨得多：4 个"最直觉的修法是错的"bugfix 任务，模型固定，每组跑 20 次，隔离的 git workspace，用 agent 看不到的 hold-out 测试来打分。

| 组别 | 成功复现问题 | 单次成本 |
|---|---|---|
| 不给任何指令 | 2/20 | \$0.176 |
| 长度相当的安慰剂文本 | 0/20 | \$0.192 |
| Superpowers 的 systematic-debugging（291 行） | 8/20 | \$0.316 |
| 自己写的 repro-first 规则（31 行） | 10/20 | \$0.241 |

31 行赢了 291 行，还便宜 24%。长度买不到服从。

另一个 [issue #1953](https://github.com/obra/superpowers/issues/1953) 里，一位用户先让 Opus 裸跑一个 case，7 万 token 加上 5.7 万做 code review，一共 12.7 万，结果基本上是完美的。然后他把目录复制一份装上插件跑同一个 case，**90 万 token，结果基本一样。**

7 倍的开销，换回来的是"差不多"。

而最有说服力的自我否定，来自项目自己的 release notes。v6.1.0 里，他们把那些按 harness 分类的工具映射参考全部裁掉了，理由是那些啰嗦的对照表，重述的是现代 agent 本来就会遵循的东西。同一个版本里还拿掉了 Codex 的 SessionStart hook，因为 Codex 自己就能可靠地触发 skill，那个引导 hook 让体验变差而不是变好。

再往前翻，v5.0.6 记录了一次更彻底的推翻：他们原本设计了一个 subagent review loop 专门派 agent 去审查计划，测下来执行时间翻倍、多花 25 分钟，而跨 5 个版本每版 5 次的回归测试给出的质量分完全相同。

### 机制上为什么会这样

前面都是现象，底下的机制有四层。

**指令冲突。** 在提示词里硬编码复杂而脆弱的逻辑，想以此逼出精确的 agent 行为，换来的是脆弱性和越来越高的维护成本，这一条写在 Anthropic 的[官方工程博客](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)里。Claude Code 团队自己也栽在这上面。他们翻内部记录时发现，同一次请求里系统提示词一边说"适当保留文档"，另一边写着"不要写注释"。

冲突不是外行才会犯的错。**因为冲突是攒出来的**——没有谁会在一天之内写下两条互相打架的规则，它们总是隔着几个月，各自解决着各自的问题。

**数量本身。** 就算规则之间完全不冲突，多也是一种问题。东京大学松尾研的团队做了两个基准专门测这件事，跑了 10 个模型，结论是指令数量一涨，表现就稳定地往下掉（[arXiv 2509.21051](https://arxiv.org/abs/2509.21051)，EMNLP Findings 2025）。还有个发现更实用：**光拿"指令有几条"这一个变量做逻辑回归，就能以大约 10% 的误差预测模型的表现**，连没见过的指令组合都能预测。条数本身就携带了那么多信息。你写了什么内容，反而没有"你写了几条"重要。

同一个团队更早的一份稿件里，给这个现象起过一个名字叫"指令的诅咒"，并提出全部指令都被满足的概率约等于单条满足率的 N 次方。那是指数级的衰减。这个名字和公式在正式发表的版本里都没再出现，所以我只当它是个形象的说法。但方向是清楚的：**每多加一条规则，付出的代价都比你以为的大。**

**注意力预算。** 还是那篇官方文章的说法：模型在解析大量上下文时，动用的是一份有限的"注意力预算"，每多一个 token 都在消耗它，所以上下文必须被当成有限资源来对待，边际收益递减。他们给上下文工程定的目标是找到能最大化达成目标概率的、尽可能小的高信号 token 集合。注意那个"尽可能小"。它和大多数人写文档时"尽可能全"的直觉，指向完全相反的两种写法。

这条源自注意力机制本身，跟哪一代模型没什么关系。[Context Rot](https://www.trychroma.com/research/context-rot) 那份报告横跨 18 个前沿模型，发现性能随输入长度的衰减是非均匀的，单独一个干扰项就足以拉低准确率。另一项研究设计得更刁钻，让问题和答案刻意不共享字面词汇，结果在 32K token 长度上，多数模型跌破了自己短上下文基线的一半。换代能缓解，但没有哪一代能免疫。

**位置。** Lost in the Middle 那个经典结论：相关信息放在上下文中部时，性能下降超过 30%，画出来是条 U 型曲线。

把四层叠起来看，几十万 token 的 skill 注入干的事情就不只是占地方了——**它把你真正想说的那句话，推到了 U 型曲线的谷底。**

## 为什么你发现不了

到这里为止，讲的都是"会出问题"。但如果问题这么明显，为什么大家还在往里加？

因为这件事**没有反馈**。

有篇论文专门测了这个，《The Compliance Gap》（[arXiv 2605.01771](https://arxiv.org/abs/2605.01771)）。它的开场是一个场景：审计员要求 AI 助手逐个打开文件，明确说了不许用脚本、不许派 agent。AI 回答"好的"，然后发出一个批量调用，一次把五十个文件全总结完了。

他们跑了 13 组实验、2031 个 session、6 个前沿模型。默认环境下，六个模型的指令服从率全是 0%。其中一个被单独拎出来写进了摘要：口头答应十次，十次全部绕过。

服从的分布还很不均匀：在能拿到奖励的地方（比如留审计轨迹）服从率 97%，在拿不到奖励的地方（逐个读文件、隐私脱敏）只有 0% 到 4%。而把派发工具从环境里移除之后，服从率跳到 75%，效应量 Cohen's d = 2.47。作者由此判断：问题出在环境给了它什么工具，跟模型权重里缺了什么没关系。

翻译成人话：**决定模型听不听话的，是它手里有什么工具，跟你把话说得多重没有关系。** 你把指令从"请尽量"改成"你必须"再改成"这不容商量"，改变的只有你自己的心理感受。

但这篇论文里最该被记住的是最后一个实验：他们找了 9 位评审做盲测，判断某个 session 到底有没有遵守指令，评审之间的一致性 Fleiss' κ 只有 0.130，**15 个真正服从了的 session，一个都没被认出来。**

你写下的那条规则到底有没有被执行，光看输出是看不出来的。

这解释了配置膨胀的整条路径。**每一次单点添加都是局部最优**：模型犯了个错，你加一条规则，下一次它没犯同样的错。不管这是因为规则起了作用，还是因为它本来就不会再犯。你得到了正反馈，于是继续加。

而反方向的动作从来不会自然发生。没有哪一天模型会告诉你"第 37 条规则今天开始变成负担了"，也没有任何一个时刻会有人跳出来问一句"这堆东西现在整体上还成立吗"。加了有反馈，删了没反馈，两边的激励完全不对称。

我那 200 多个 skill 就是这么攒出来的。每一条写下的当天都对着某个具体的失败，合在一起之后就再没人检查过它们彼此是否还相容。

还有一层更隐蔽的不对称。**添加几乎没有风险，删除有。**

加一条规则，就算它完全没用，也不会有任何人来找你麻烦，最坏的结果是它静静躺在那儿，把成本摊进你每一次调用里，而这笔账没人算得清。但删掉一条规则之后，只要模型在那个方向上出了一次错，你立刻会怀疑是不是删错了，哪怕它跟这次出错毫无关系。

加错了没人会怪你，删错了要自己背。所以但凡犹豫一下，选的都是继续加。

这个结构我在别处见过。任何一个跑了三年以上的代码库里都躺着大量死代码，所有人都知道该删，但没人愿意当那个删的人——因为删对了没有任何奖励，删错了要背责任。提示词的处境差不多，区别是代码库里的死代码好歹是静态的，而提示词是活的，它会主动参与每一次推理。死代码只是占地方，死提示词会插嘴。

## 身份类不会过期

写到这里，可能给人一种"提示词都该删光"的印象。我不这么认为，而且反例就在同一批材料里。

**删错地方是真的会掉分的。** Superpowers 的 v6.2.0 做了一轮全面压缩，把回顾段落、社会认同、卖点铺陈这类文字全清了。但有一处清完出了事：TDD 那个 skill 的"Why Order Matters"章节，整段拿掉之后，在"先写代码、测试后补"的压力测试下，**遵守测试先行的比例从 8/10 掉到 5/10**，Claude 和 Codex 上都复现了。

他们最后的处理方式值得抄。章节还是删了，但把里面每一条反驳拆开，塞进"常见的自我合理化"对照表的对应行里。章节没了，可当 agent 正在给自己找借口的那一刻，对应的那句反驳会当场打过去。删不删从来不是重点，**放在哪一层**才是。

**裸模型也远远不够。** 回头看前面那组对照实验里最容易被忽略的一行：不给任何指令的那组只有 2/20，加了规则之后跳到 8 到 10。四倍的提升。而长度相当的安慰剂文本是 0/20，起作用的是规则的机制，跟长度无关。规则有用，只是不需要写 291 行。

这组数据的边界也得说清楚：4 个小任务、每组 5 次、所有组的正确率都饱和在 20/20，所以它只测到了"能不能复现问题"这一个轴，完全没有触及真实代码库上的根因质量，而那恰恰是完整流程最可能把成本赚回来的地方。这属于未测试的轴，不能当成零结果。这个边界比结论本身更值得记住。

**Anthropic 一边删提示词一边在推 Agent Skills，这两件事不矛盾。** 官方那篇 [Agent Skills 的设计文章](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)讲得很清楚，skill 的核心是三级渐进式披露：启动时只加载 name 和 description，判断相关了才读正文，引用到了才读附加文件。它要补的是模型天生没有的东西：操作 PDF 表单这类能力缺口、组织内部的私有知识、必须严格按序执行的流程。

**这三样，全都是第三类。**

官方要拦的是另一件事：把 skill 当系统提示词用，也就是全量常驻、高压措辞、把模型已经会的事再讲一遍。那个 SessionStart 全文注入，恰好把渐进式披露这个设计整个绕过去了。

顺便说一句，Anthropic 自己的 [Skill 编写文档](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)教的全是怎么少写。它给的第一句话是**上下文窗口是公共资源**，默认假设写得更直接：Claude 已经很聪明了，只补它还不知道的东西。然后要求你对每一条信息发起挑战："Claude 真的需要这段解释吗？""这一段值它花掉的 token 吗？"硬指标是正文控制在 500 行以内。

它还建议你按模型分别测试：给 Haiku 测的是"指引够不够"，给 Sonnet 测的是"清不清晰"，而给 Opus 这种强推理模型，测的是**有没有解释过头**。

同一份文档，对弱模型问"够不够"，对强模型问"多不多"。

还有第三种主张，方向跟"删"完全相反：解法是加法。别把规则塞进一个大 prompt，改成一条条带触发条件的准则，只在相关时才加载。这套东西在 [Parlant](https://github.com/emcie-co/parlant) 里实现了（我查的时候 18,178 star），每条准则拆成"条件 + 动作"，每轮对话先做一次轻量匹配，只把命中的注进上下文。

这其实还是渐进式披露，只是把粒度做到了单条规则上。你的规则要真是几百条业务约束，删是删不掉的，那就只能在加载时机上做文章。但这条路底下有个反驳更狠：一旦你发现自己在疯狂堆脚手架来提升表现，通常还不如直接等下一代模型出来。

这两种立场赌的是不同的时间尺度。你要是今天就得上线一个客服 agent，工程化管理几百条业务规则是唯一能走的路；你要是在给自己的编码 agent 攒 skill，那"等下一代模型"确实经常是更优解，因为对你来说，等待的成本几乎是零。

## 那你删什么

三类分完，动作就很清楚了。

如果只想先花五分钟试试水，那就打开你最长的那个 skill，只看前 20 行，挨句问一遍：这些话模型现在还需要听吗？只要开始问这个问题，该删的东西自己就会浮出来。

想做得彻底一点，就按三类分头处理。

**补丁类，直接删。** 它们对应的模型缺陷大概率已经被修掉了，留着只会跟新模型的默认行为打架。我打算按"这条规则是哪一代模型时期写的"来筛，凡是超过两个大版本的，先删了再说。

**能力类，删掉九成。** 那些讲怎么用 git、怎么写测试、怎么组织代码、怎么做代码审查的篇幅，模型读过的版本比我写的多得多。只保留一种情况：这件事有多种主流做法，而我们团队明确选了其中一种。那已经属于第三类了。

**身份类，值得花时间写好。** 仓库的坑、团队的规范、部署的顺序、我的偏好。这些内容我现在写得最少，却是唯一不会过期的。

还有一条推论：**从别人那里下载来的 skill，大概率最先该删。** 一个能被公开分发、装在成千上万台机器上的 skill，按定义就不可能是谁特有的。它要么在讲通用最佳实践（第二类），要么在讲它作者的工作习惯（那是他的第三类，不是你的）。真正只有你这儿成立的东西，从来没有人替你写好过。

那 200 多个里，自己写的和装来的大概各占一半。我打算先动装来的那一半。

具体怎么动，有两件事必须做在前面。

**留一条回滚的路。** TDD 那个章节就是现成的教训。删错一段，合规率从 8/10 掉到 5/10，而这件事只有测了才知道。最理想的做法当然是先挑三五个能重复跑的典型任务当基准，删一段测一次。但真没这个条件也别因此不动手，最低限度是把删掉的内容单独存一份，记上删的日期，出了问题能原样贴回去。**有回滚就敢删，敢删才有得测。**

**长的拆开，别整段常驻。** 渐进式披露这件事说了很久我一直没做，因为拆文件比写文件麻烦。但 6.7 万字节那个文件躺在那儿，一个月触发不到一次，每次触发还得整个读进来，这笔账怎么算都不划算。

**给新加的规则写上日期。** 这条最简单也最容易被跳过。补丁类过期的前提是你能认出它是补丁，而过上几个月，你根本想不起来某条规则当初是为了对付什么。我打算以后每加一条就在后面缀一句"为了 XX 问题加的，某年某月"。一行注释的成本，换的是将来能不能判断它还该不该留。

有个问题我没想清楚：这个"减"的动作到底该多久做一次。模型每次大版本更新都重来一遍？那维护成本会不会比省下来的还高。Claude Code 能一次删掉 80%，前提是先攒下了那 80%；要是每个月都清一次，可能根本攒不到，也可能纯属白忙。

更麻烦的是，删除本身也需要判断力，而判断力这东西没法自动化。`claude doctor` 这类工具能帮你找出重复和冗长，但它没法替你回答"这条规则讲的是不是只有我知道的事"，那个答案只在你脑子里。工具能替你删的都是最好删的那批，剩下的还得自己啃。

## 没有人会提醒你

那 200 多个 skill 是我一条一条攒起来的，每一条当初都对着一个具体的问题。那时候模型确实不会，也确实需要教。问题在于这半年多我只做了加法。

加法本身没错，错在从来没有回过头。这期间模型换了好几代，那些规则一条都没重新审过，它们还在按当初那个模型的样子约束着现在。

更麻烦的是，这件事不会给你任何提示。前面那个盲测已经说明了：**连专门去找的人都认不出模型到底有没有照做，你在自己的配置面前只会更认不出来。** 某条规则是在起作用、在被忽略，还是在帮倒忙，光看结果分不出来。

而分不出来的东西，没人会主动去删。

所以这件事不会自己发生，得专门腾出一个下午。把那些当初写得最用力的规则一条条翻出来，挨个问一句：它当年对付的那个毛病，现在还在吗？

删起来很快，难的是删完之后忍住不再往回加。

这件事的范围比 skill 大得多。一条团队规范、一个上线检查项、一段沿用了三年的流程，当初都对着一个真实的问题，后来问题没了，规矩还留着。不会有人站出来说这条已经不需要，因为那个通知从来就不存在。

区别只在于，别的规矩过期了，最多让人多走几步冤枉路。提示词过期了，替你走冤枉路的是模型。

所以别等下一次模型更新了。打开你的 Claude Code 或者 Codex，把 CLAUDE/AGENTS.md 和最长的那几个 skill 丢给它，问一句：这里面哪些内容已经内化到模型里面了？

然后看着它一条条划给你，然后删除它。
